## 需求 1：文本节点增加 Gemini 模型

### 现状

- 渠道系统原生支持 Gemini：[use-config-store.ts](../web/src/stores/use-config-store.ts) 中 `ApiCallFormat` 已含 `"gemini"`，默认渠道即预置 Gemini 渠道（`baseUrl = https://generativelanguage.googleapis.com`，`apiFormat: "gemini"`），且默认文本模型列表里已有 `gemini-3-pro-preview`。
- Gemini 协议调用模板已存在：`web/src/services/api/model-templates/text.gemini.js`。
- 文本节点模型选择走 `selectableModelsByCapability(config, "text")`，任何渠道里 capability 为 `text` 的模型都会出现在文本节点模型列表中。

### 方案

代码能力已齐，不需要新增协议支持。建议做两件事：

1. **配置引导**：确认 Gemini 渠道填入 API Key 后文本节点可选 Gemini 文本模型（`gemini-3-pro-preview` 等）；若用户使用的是 Gemini 兼容中转站，在渠道编辑里新建渠道、`apiFormat` 选 Gemini、填 Base URL / Key / 模型名即可。
2. **默认预设微调（可选）**：若希望「开箱即用」，在 `use-config-store.ts` 的 `defaultChannels` Gemini 渠道里按需补充常用文本模型名（如 `gemini-2.5-flash`、`gemini-2.5-pro`）；已持久化过配置的老浏览器不会自动出现，需要用户手动在渠道里添加或重置配置。

### 待确认

- 试用方用的 Gemini 是官方直连还是中转站地址（决定默认 Base URL 是否要调整）。

## 需求 2：图片节点增加 GPT Image 模型

### 现状

- 默认 OpenAI 渠道已预置图片模型 `gpt-image-2`（`capability: "image"`）。
- 生图请求走 `web/src/services/api/image.ts`，支持文生图与参考图编辑（edit），与 GPT Image 系列接口兼容。
- 图片节点的模型、尺寸（size）、质量（quality）、张数（count）等参数已由图片设置浮层（`web/src/components/canvas/canvas-image-settings-popover.tsx`）控制。

### 方案

与需求 1 同理，能力已具备，主要是配置项确认与预设：

1. 确认 `gpt-image-2`（或渠道商提供的 `gpt-image-*` 系列模型名）已在某个渠道的模型列表中且 capability 为 image；渠道编辑抽屉（`web/src/components/layout/channel-editor-drawer.tsx`）支持手动添加模型并指定能力类型。
2. 模型名智能识别 `guessCapability()` 的 `IMAGE_KEYWORDS` 已包含 `gpt-image`，手动输入模型名时会自动归为图片能力，无需改代码。
3. 若中转站模型命名不含 gpt-image 关键字（如自定义别名），在渠道编辑里手动把能力类型设为「图片」即可。

### 待确认

- 中转站上 GPT Image 的确切模型名，以及是否需要走自定义调用脚本（项目已有「模型脚本」机制兜底）。

## 需求 3：生成时在原节点生成（不另跳新节点）

### 现状

- 项目已有该行为的全局配置：`AiConfig.nodeRegenerateBehavior: "new-node" | "overwrite"`（[use-config-store.ts](../web/src/stores/use-config-store.ts#L57)），默认值为 `"new-node"`（另跳新节点）。
- 配置入口在设置弹窗「偏好设置」里：[app-config-modal.tsx#L272-L283](../web/src/components/layout/app-config-modal.tsx#L272-L283)。
- 生成逻辑按该配置分流：[project.tsx#L2369](../web/src/pages/canvas/project.tsx#L2369) `overwriteExisting = effectiveConfig.nodeRegenerateBehavior === "overwrite"`；图片模式下 `overwriteExisting` 或「空图片节点」时会复用原节点（`reuseImageNode`），否则新建节点。

### 方案

1. **默认值反转（改动最小）**：把 `defaultConfig.nodeRegenerateBehavior` 默认值从 `"new-node"` 改为 `"overwrite"`，同时调整 `merge()` 中的归一化逻辑与配置弹窗的默认选中项。这样试用方开箱即是「原节点生成」。
   - 注意：已保存过配置的浏览器沿用旧值，需在设置里手动切换一次，或按仓库「不做旧数据兼容」约定直接不管。
2. **补充多张生成时的行为确认**：`overwrite` 模式下若张数 `count > 1`，当前实现是复用根节点 + 挂子图（`pendingChildIds`），需实测确认多图场景表现符合预期；不符合再微调 project.tsx 中图片分支的节点复用逻辑。
3. **可选增强**：在节点悬浮工具栏加一个「生成到原节点 / 新节点」快捷开关（写 `nodeRegenerateBehavior`），避免每次去设置弹窗改。此项为锦上添花，可不做。

### 风险

- 「原节点覆盖」会把原图替换掉，用户可能误覆盖；配合需求 4（组合图）时建议保留「新节点」作为兜底选项。

## 需求 4：图片节点群组后合并成一张新的组合图

### 现状

- 群组能力已有：`CanvasNodeType.Group`（[canvas.ts](../web/src/types/canvas.ts#L18)），快捷键 `Ctrl/Cmd + G` 打组、`Ctrl/Cmd + Shift + G` 解组。
- 生成上下文已支持读取群组内所有子节点资源：`getGroupResourceNodes()`（`web/src/lib/canvas/canvas-resource-references.ts`）+ `buildNodeGenerationInputs()`（[canvas-node-generation.ts](../web/src/components/canvas/canvas-node-generation.ts#L128-L136)），即「把群组作为参考图集合喂给生图模型」的数据链路已经通了。
- 目前没有「合并成一张图」的动作入口。

### 方案（推荐分两级实现）

**A. 本地拼图合成（纯前端、免费、即时）**

1. 在群组节点的右键菜单 / 悬浮工具栏加「合并为一张图」动作。
2. 取群组内所有图片子节点，按画布上的相对位置（或网格布局）用 Canvas API 拼合成一张位图，输出为新图片节点（并落「我的素材」存储，复用现有 `uploadImage` / 图片存储逻辑）。
3. 可选参数：行列数、间距、背景色，第一版可以固定网格布局。

**B. 走生图模型合成（效果更好、消耗算力）**

1. 同一入口提供「AI 合成组合图」选项：把群组内图片作为参考图列表 + 一段默认提示词（描述「将这些图片组合成一张图」），走现有 `requestEdit`（参考图编辑）链路生成一张新图。
2. 数据准备复用 `buildNodeGenerationContext` 对 Group 的支持，几乎不需要新协议代码，只需组装调用与结果落点。

建议先做 A（快、零成本），B 作为进阶选项。

### 涉及文件

- 群组节点菜单/工具栏：`web/src/components/canvas/canvas-context-menu.tsx`、`canvas-node-hover-toolbar.tsx`
- 拼图工具函数：建议放 `web/src/lib/canvas/`
- 新图落点与存储：`web/src/pages/canvas/project.tsx`（复用现有插入图片节点逻辑）、`web/src/services/image-storage.ts`

## 需求 5：滚轮移动画面 + 左键直接选择

### 现状

交互入口集中在 [infinite-canvas.tsx](../web/src/components/canvas/infinite-canvas.tsx)：

- `handleWheel`（L87）：滚轮目前是**缩放**（以鼠标位置为中心）。
- 默认工具是 `"pan"`（[project.tsx#L233](../web/src/pages/canvas/project.tsx#L233)），即背景左键拖拽 = 平移；按住 Ctrl/Space 临时切换到 select，**Ctrl + 左键拖拽 = 框选**——这正是试用反馈「选择要按 Ctrl+左键」的来源。
- 单个节点的选中其实已经支持纯左键点击（`selectNodeByEvent`，Shift/Ctrl 才是追加选择）。
- 快捷键文档：`docs/content/docs/canvas/canvas-shortcuts.zh-CN.mdx`。

### 方案

1. **滚轮改为平移**：改 `handleWheel`，用 `event.deltaX / event.deltaY` 直接平移 viewport（`x += -deltaX * step`，`y += -deltaY * step`；触摸板双指自然滚动方向需实测调一次符号）。
2. **缩放移到 Ctrl + 滚轮**：`handleWheel` 里 `event.ctrlKey` 时走现有缩放逻辑；同时保留底部缩放控件（`canvas-zoom-controls.tsx`）与 +/- 快捷键作为兜底。
3. **默认工具改为 select**：`project.tsx` 中 `useState<"select" | "pan">("pan")` 改为 `"select"`——背景左键拖拽 = 框选（`handleCanvasMouseDown` 已实现），左键点击节点 = 选中；平移靠滚轮 + 中键拖拽 / 空格拖拽（现有 Space 临时平移逻辑保留）。
4. **同步文档**：更新 `canvas-shortcuts.zh-CN.mdx` / `.en-US.mdx` 的「视图」「选择」章节。

### 待确认

- 滚轮平移后，原本习惯滚轮缩放的用户需要适应；建议在缩放控件旁保留缩放滑杆即可，不加额外设置项（如确需保留「滚轮=缩放」模式，可加一个偏好开关，但这与 AGENTS「避免多余分支」原则冲突，默认不加）。

## 需求 6：选择模型和分辨率后显示用了多少算力

### 现状

- 项目目前**没有任何算力/积分/计费概念**（全局检索无 credit/算力相关业务代码），AI 调用是浏览器直连用户自己的 API，费用发生在渠道商侧。
- 模型与分辨率的选择位置：图片设置浮层 `canvas-image-settings-popover.tsx`（模型、size、quality、count）、文本/视频/音频各有对应 settings popover。

### 方案（两种思路，取决于数据来源，需先确认）

**思路 A：静态估算表（不依赖接口，先做这个）**

1. 在渠道模型定义上扩展一个可选的 `costHint`（如「每次 2 算力」「1K 1 算力 / 2K 3 算力」），由用户在渠道编辑里自行填写（不同中转站计费不同，无法内置统一价格）。
2. 在各设置浮层底部加一行只读文案：`预计消耗：{模型 costHint} × {count} 张`，随模型 / size / count 选择即时更新。
3. 优点：零外部依赖、贴合纯前端架构；缺点：数字靠人工维护，只是估算。

**思路 B：实时余额查询（依赖中转站能力）**

1. 多数 OpenAI 兼容中转站提供余额查询接口（如 `/v1/dashboard/billing/...` 或站点自定义接口）。在渠道配置里加「余额接口路径」可选项，前端定时/手动拉取当前余额并显示在顶栏或设置浮层。
2. 「本次将消耗多少」仍需要思路 A 的估算表配合，余额接口只能给「还剩多少」。
3. 优点：接近真实算力；缺点：各站接口不统一，逐站适配，且浏览器直连可能遇到 CORS。

### 待确认（关键）

- 试用方使用的渠道商是哪一家？其计费单位（算力/额度/美元）与是否有余额查询 API？
- 「算力」是指渠道商的积分体系还是需要项目自建一套用户额度体系？后者涉及后端/账号体系，与当前纯前端架构冲突，工作量远大于前端改造，需明确范围。
